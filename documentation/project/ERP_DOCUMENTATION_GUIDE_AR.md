# دليل توثيق ERP العام

هذا هو المدخل العملي لتوثيق أي موديول أو ميزة جديدة في ERP System. الدليل
ينطبق على Platform وHR وAccounting وأي موديول لاحق مثل Inventory أو Sales أو
POS، ويحافظ على كتب HR الحالية دون اعتبارها متطلبات عامة لكل النظام.

فهرس ما يمكن إعادة استخدامه موجود في
[SHARED_REUSE_CATALOG.md](SHARED_REUSE_CATALOG.md). هذا الفهرس جزء من دورة
العمل المستمرة وليس صفحة مرجعية اختيارية.

ولأن توحيد تجربة الاستخدام جزء من ملكية النظام، يجب قراءة
[SCREEN_PATTERN_CATALOG.md](SCREEN_PATTERN_CATALOG.md) قبل إنشاء أو إعادة بناء
أي شاشة. النمط المسجل له معرف ثابت (`P-###`)؛ لا يكفي وصف عام مثل "شاشة CRUD"
في الخطة.

## قاعدة الملكية

الجدول يحدد **ملكية التوثيق والحدود المستهدفة**. لا يعني إدراج مسؤولية أن
الخدمة أو الموديول منفذ حاليًا؛ الحالة المثبتة تأتي من المصدر والاختبارات
والـmanifest فقط.

| المالك | ما يملكه | ما لا يملكه |
| --- | --- | --- |
| Platform | الهوية، الجلسة، Tenant وCompany، تفعيل الموديولات، الصلاحيات العامة، سياق الطلب، والبنية التشغيلية المشتركة | قواعد أعمال HR أو Accounting، أو جداول موديول آخر |
| الموديول | قواعد المجال، الكيانات، العقود، حالات الاستخدام، الصلاحيات الخاصة، الـAPI، ومصادر بياناته وترحيلاته | الوصول إلى EF/Infrastructure لموديول آخر أو نسخ وظائف Platform |
| Shared/BuildingBlocks | أنواع وأدوات محايدة مستخدمة فعليًا في أكثر من موديول | كيانات الأعمال، مستودعات عامة تربط الموديولات، وقواعد HR أو Accounting |
| Host وShell | تركيب الموديولات، التسجيل، الحماية العامة، TopBar وSidebar والتنقل العام | منطق المجال أو منح صلاحية لا يمنحها الخادم |

## أين تكتب الوثيقة؟

ابدأ بملف الموديول في `documentation/modules/<slug>/`. يحتفظ الموديول
بـ`README.md` و`ARCHITECTURE.md` و`DELIVERY-ROADMAP.md` وفهرس الميزات وقرارات
API/web/mobile الخاصة به. الكتب العامة التي تنطبق على أكثر من موديول تبقى في
`documentation/project/` أو `documentation/system/`.

لكل ميزة مكتملة يجب أن توجد أدلة مترابطة لما يلزم من الكتب الأربعة:

```text
master review       ← القرار والملكية والعقد عبر النظام
api profile         ← HTTP، الصلاحيات، البيانات، والاختبارات
web profile         ← Next.js، التنقل، الواجهة، والترجمة
mobile profile      ← Expo، التنقل، الاتصال، وOffline إن كان مطلوبًا
```

يجوز أن تكون الكتب الجديدة داخل حزمة الموديول، مثل
`documentation/modules/accounting/features/chart-of-accounts/`، إذا سجلها
الـmanifest بهذه المسارات. لا تنشئ نسخة ثانية من كتاب قائم؛ كتاب HR الحالي
يبقى في مساره المرجعي وتقوم حزمة HR بفهرسته فقط.

## طريقة بدء ميزة جديدة

1. شغّل `./documentation/system/Generate-Documentation.ps1 -Check` وسجّل
   النتيجة قبل تعديل المصدر.
2. حدد الموديول المالك، ونطاق البيانات (`global` أو `tenant` أو `company`)،
   وامتلك قرارًا صريحًا للاعتماديات مع Platform والموديولات الأخرى.
3. ابحث في [فهرس إعادة الاستخدام](SHARED_REUSE_CATALOG.md) وBuildingBlocks
   ومكونات الموديول قبل إنشاء شيء جديد، وسجل ما أُعيد استخدامه أو تمديده أو
   رفضه في طلب التنفيذ وكتاب الميزة. هذه الخطوة إلزامية قبل **كل** ميزة، حتى
   لو كانت الميزة داخل نفس الموديول.
4. اختر Pattern ID من كتالوج أنماط الشاشات، أو افتح إضافة نمط جديدة إذا لم
   تنطبق الأنماط الحالية. سجّل Web/Mobile applicability، اختلاف layout المقصود،
   ومراجع المصدر والاختبارات في feature profile و`required-files.json` عند
   الحاجة. كل نمط جديد أو تغيير جوهري في نمط قائم يجب أن يراجع نفس الرحلة في
   Web وMobile ويسجل لكل منصة `Implemented` أو `Adapted` أو `Deferred` أو
   `Excluded`، ويحدّث دليلي المنصتين في نفس التغيير. لا تُنشئ نسخة look-alike
   محلية لنمط موجود.
5. جمّد العقد: الحقول والعلاقات، الصلاحيات، دورة الحياة، الأخطاء، paging/sort،
   أحداث التكامل، والتحديث اللحظي. لا تعتبر DTO أو migration وحدها تنفيذًا.
6. قرر لكل من API والويب والموبايل هل capability هي `Required` أو `Deferred`
   أو `Excluded`، بما في ذلك Import وReport وOffline read/write.
7. نفذ الشريحة كاملة في الموديول المالك، ثم حدّث ملفات الأدلة والـmanifest
   وشغّل التحقق. للـflow الجديد: Phase 06 هي Verification & Acceptance ويجب أن
   تنتهي بـ`Verified` قبل بدء Phase 07 الخاصة بتوثيق العميل والفيديو والإغلاق.

## دورة التحسين المستمرة للمكونات المشتركة

عند إعادة استخدام أو إضافة أو تمديد مكوّن مشترك، حدّث دليله العام في نفس
التغيير. يجب أن يوضح الدليل الـpublic API والخيارات والقيم الافتراضية، مثال
استخدام حقيقي، القيود، RTL وإمكانية الوصول، حالات التحميل والخطأ، التوافق،
والاختبارات. اربط كل مستهلك متأثر بملف feature profile الخاص به، وسجّل قرار
`Required` أو `Deferred` أو `Excluded` لكل منصة. ثم أعد توليد الحزم عندما تتغير
أقسام مرقمة أو مصادر وصفة. لا توجد ترقية إلى Shared لمجرد أن قطعتين تشبهان
بعضهما؛ يجب أن تكون القدرة محايدة للمجال ومستخدمة فعليًا من أكثر من موديول.

## استخدام مولّد التوثيق بدقة

للعمل المخطط، الأمر `New-FeatureDocumentation.ps1` يستقبل `PlanId` و
`SliceId` و`Module` لربط التنفيذ بالخطة والشريحة المصرح بها. خيار
`ReferenceFeature` اختياري ويستخدم فقط عندما يوجد مرجع تنفيذي مناسب فعلًا؛
`none` صحيح للميزات التي لا يشبهها Countries أو States.

المولّد يخطط مبدئيًا لكتب مركزية تحت `documentation/project/` و`documentation/api/`
و`documentation/web-next/` و`documentation/mobile-react/`. بالنسبة لميزة أعمال
جديدة، شغّل المولّد للحصول على الـdraft، ثم عدّل **بصورة مقصودة** مسارات
`plannedCanonicalBooks` و`requiredFiles` و`recipe-registration.draft.json` إلى
كتب الموديول المالك إن كان ذلك هو قرار الملكية. يجب أن توجد الكتب الأربعة
المعلنة، وأن تستخدم الوصفات أقسامًا مرقمة موجودة فعلًا، قبل نقل draft إلى
manifest النهائي. لا تنسخ قواعد CRUD من Countries أو HR؛ انقل فقط طريقة التحقق
ثم أعد تقرير الحقول والملكية والعلاقات والتعارضات من الصفر.

استخدم معرفات فريدة مسبوقة بالموديول، مثل
`accounting-chart-of-accounts` أو `pos-shift-closing`. الميزات الجديدة
المرتبطة بخطة تستخدم Phase 00 Implementation Preflight ثم 01–05 للتنفيذ ثم
Phase 06 Verification & Acceptance ثم Phase 07 Customer Education & Closure.
الوصفات تكتب مخرجاتها تحت
`documentation/system/generated/<feature-id>/`. الوصفات المسجلة تاريخيًا
بـ00–06 تظل مستقرة ولا يعاد ترقيمها لمجرد التماثل. لا تعدّل `generated/`
يدويًا.

## دليل القرار للـOffline في الموبايل

لا تجعل Offline وضعًا عامًا إجباريًا. لكل ميزة وعملية قرار مستقل على mobile:

| القدرة | القرار المطلوب |
| --- | --- |
| قراءة محفوظة | مصدر البيانات، مدة الصلاحية، آخر تحديث، وحدود البحث المحلي |
| كتابة محلية/مسودة | ما الذي يعد مسودة، وكيف تحميه، ومتى يصبح معتمدًا |
| كتابة قابلة للمزامنة | outbox، idempotency، retries، التعارض، والنتيجة غير المؤكدة |
| اتصال مطلوب | العمليات التي لا يجوز تنفيذها دون تحقق لحظي من الخادم |

سجل أيضًا إعداد Tenant/Company، وصلاحية المستخدم، وإمكانية تعطيل الميزة،
وتشفير التخزين، وتسجيل الخروج أو تغيير الشركة، وترقية قاعدة البيانات المحلية،
والحد الأقصى للبيانات. لا تعرض العملية كنجاح نهائي قبل وصول تأكيد الخادم.

## بوابة القبول قبل اعتبار الميزة جاهزة

- المصدر مملوك للموديول الصحيح ولا توجد مراجع مباشرة لداخل موديول آخر.
- العقد والصلاحيات والعزل بين Tenant/Company موثقة ومختبرة.
- API والويب والموبايل يملكون فقط الأسطح المصنفة Required، والاختلافات مقصودة.
- المكونات المشتركة أُعيد استخدامها أو سُجل سبب إنشاء البديل محليًا.
- كل شاشة جديدة مسجلة بـPattern ID ثابت، ومراجع الويب/الموبايل وحالاتها
  واختباراتها مربوطة بكتاب الميزة؛ وإذا اختلفت المنصتان فالاختلاف مقصود وموثق.
- إذا أُضيف أو مُدّد مكوّن مشترك، فدليله العام ومستهلكوه محدثون في نفس التغيير
  مع API والخيارات والقيود والاختبارات وقرارات المنصات.
- اختبارات النوع والبناء والميزات وفحص الحدود و`git diff --check` ناجحة.
- تم تشغيل Generate ثم `Generate-Documentation.ps1 -Check`، وسجلت مرحلة 06
  النتائج والقيود وخطوة الإصدار التالية.

## مراجع HR الحالية

كتب Countries وStates وAddresses وغيرها تحت `documentation/project/` وملفات
API/web/mobile المرتبطة بها هي أدلة HR الحالية. استخدمها كنماذج تحقق فقط،
وسجل أي اختلاف في كتاب الموديول الجديد. وجود رابط HR لا يعني أن الميزة عامة
ولا يعني أن سطحًا على منصة معينة منفذ.
