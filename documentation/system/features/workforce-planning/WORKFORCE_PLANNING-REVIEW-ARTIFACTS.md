## Lifecycle and invariant tables

| Aggregate | Allowed transitions | Non-negotiable invariant |
| --- | --- | --- |
| FiscalYear | Existing lifecycle only | Workforce approvals and reservations require Open |
| WorkforcePlan | Draft -> Submitted -> UnderReview -> Approved/Rejected; Approved -> Superseded | One effective revision; period slot sum equals PlannedHiringSlots |
| WorkforceBudget | Draft -> Submitted -> Approved/Rejected; Approved -> Superseded/Closed | AuthorizedHeadcount <= PlannedHiringSlots; category allocations reconcile |
| PositionEnvelope | System-generated active snapshot | Available headcount and salary never fall below zero |
| EnvelopeAmendment | Draft -> Submitted -> Approved/Rejected | Positive deltas only; requester cannot approve |
| StaffingRequest | Draft -> Submitted -> Approved/Rejected/Cancelled/Fulfilled | Cancellation releases only the unallocated/unhired remainder |
| Planned JobRequisition | Draft -> Submitted -> Approved/Rejected/Cancelled/Fulfilled | Approved StaffingRequest and remaining quota are required |
| JobOffer | Draft -> PendingApproval -> Approved -> Issued -> Accepted/Declined/Withdrawn/Expired | Issuance requires Approved; statuses 1-6 remain unchanged |
| Hire | Idempotent command | Accepted offer, capacity transition, and Employee graph commit atomically |

## Financial policy evidence

`CalculationPolicyVersion=2026-09-V1` is frozen in the implementation request.
The authoritative commitment is the rounded fiscal-year pro-rata cost, not an
annualized display value. Every reservation stores currency, policy version,
annualized salary, fiscal-year cost, and source start date. Salary and recruitment
costs reconcile separately; a missing category allocation is a validation error.

## Database and rollout evidence

The current EF migration chain ends at the user-created
`20260906095027_RepairWorkforcePlanLinesLegacySchema`. The
read-only checks run during Phase 0 were:

```text
./documentation/system/Generate-Documentation.ps1 -Check
dotnet ef migrations list --project api/HrManagementSystem.Infrastructure/HrManagementSystem.Infrastructure.csproj --startup-project api/HrManagementSystem.Api/HrManagementSystem.Api.csproj --no-build
dotnet ef migrations has-pending-model-changes --project api/HrManagementSystem.Infrastructure/HrManagementSystem.Infrastructure.csproj --startup-project api/HrManagementSystem.Api/HrManagementSystem.Api.csproj --no-build
```

Results at the initial Phase 1 review: documentation check passed for 63 registered
recipes and `AddWorkforcePlanningPlans` was already applied. The corrective review
found legacy non-null columns in the existing empty `WorkforcePlanLines` table and
a non-unique effective-plan index. Source now models the correct invariant, so EF
required a user-created manual migration because the legacy columns were absent
from the EF snapshot. `RepairWorkforcePlanLinesLegacySchema` now contains guarded
SQL and remains pending application. No migration was created or applied by Codex,
per the user's migration-ownership instruction.

The user-created `modifyPahse01` migration replaces
`IX_WorkforcePlans_TenantId_CompanyId_FiscalYearId_Status_ActivatedOn_SupersededOn`
with the unique filtered `UX_WorkforcePlans_OneEffectivePerFiscalYear` index. The
later `RepairWorkforcePlanLinesLegacySchema` migration uses guarded SQL to drop
`EstimatedSalary`, `EstimatedRecruitmentCost`, `Q1Target`, `Q2Target`, `Q3Target`,
and `Q4Target` from `WorkforcePlanLines`, plus `SubmittedByEmployeeId`,
`ApprovedByEmployeeId`, and `ReviewNotes` from `WorkforcePlans`. It also aligns
`BranchId` as nullable, `DivisionId` as required, and removes the legacy default
constraint from `NewHireSlots`. Both affected tables were reverified at zero rows
before authoring; the migration aborts if legacy data appears before application.

Planned additive migrations are `AddWorkforcePlanningPlans`,
`AddWorkforceBudgetsAndPositionEnvelopes`, `AddStaffingRequestsAndEnvelopeAmendments`,
`LinkStaffingRequestsToJobRequisitions`, and `AddJobOfferApprovalGovernance`.
