# Realtime Application Updates

## Purpose

The application uses SignalR for live data refresh as well as persisted user
notifications. Realtime refresh messages are cache-invalidation hints; they do not
contain authoritative entity data. The client always reloads data through the
authorized API.

## Delivery Flow

```text
Command or service
    -> SaveChangesAsync succeeds
    -> BackgroundJob.Enqueue(feature changed job)
    -> persist permission-based notifications when required
    -> send ReceiveEntityChanged through SignalR
    -> web-next validates and deduplicates the event
    -> React Query invalidates affected active queries
```

Hangfire supplies durable job storage and automatic retry. The small failure window
between `SaveChangesAsync` and `BackgroundJob.Enqueue` is accepted because live UI
refresh is not business-critical. Do not add an outbox table, polling dispatcher,
leasing, or recovery service unless a future workflow has a documented delivery
requirement that justifies them.

## Event Contract

`RealtimeEntityChanged` contains:

- `EventId`: the Hangfire request operation ID, stable across retries.
- `OccurredAtUtc`: event dispatch time in UTC.
- `Resource`: a stable plural `kebab-case` value generated by
  `RealtimeResource.For<TEntity>()` and cached per entity type.
- `Action`: the feature's business action such as `Add`, `Update`, `Delete`, or `Restore`.
- `EntityId`: the affected identifier when one is available.

Never add HR records, employee details, or other sensitive payloads to this event.

## Audiences

Choose exactly one audience based on data ownership:

| Data ownership | SignalR group |
| --- | --- |
| Shared reference data | `GeneralHubGroups.ForPermission(permission)` |
| Tenant/company data | `GeneralHubGroups.ForCompanyPermission(tenantId, companyId, permission)` |
| Personal user data | `GeneralHubGroups.ForUserCompany(tenantId, companyId, userId)` |

Never use `Clients.All` for entity changes. Never accept tenant, company, permission,
or user group identifiers from a Hub method. `GeneralHub` derives all memberships
from the validated short-lived realtime token.

## Adding A Feature

1. Use `RealtimeResource.For<TEntity>()`; do not add the entity to a central list.
   The convention maps `Country` to `countries` and `AddressType` to
   `address-types`. Add `[RealtimeResourceName("...")]` only when an existing
   public resource contract needs a different name.
2. Create a feature-owned Hangfire job request containing the action, actor, scope,
   operation ID, and entity ID or response details needed for notification text.
3. Enqueue the job only after a successful database save.
4. Apply `[AutomaticRetry(Attempts = 5)]` to the job.
5. Select the narrowest valid SignalR audience.
6. Send `ReceiveEntityChanged`; keep persisted notifications permission-aware.
7. Add the resource and affected query roots to `web-next/src/features/realtime/realtimeQueryRegistry.ts`.
8. Add tests for the event contract, audience, and dependent query invalidation.

## Client Behavior

`RealtimeEntityBridge`:

- validates every payload with Zod;
- ignores duplicate event IDs;
- batches changes arriving close together;
- refetches only active matching queries and marks inactive queries stale;
- refreshes all registered active realtime queries after reconnection;
- never displays a toast for cache invalidation events.

The reconnect refresh is intentional because SignalR events are not replayed while a
browser is disconnected.

## Scaling

The current deployment assumes one API instance. Before running multiple API
instances, configure a SignalR backplane such as Redis or use Azure SignalR Service.
Hangfire already coordinates persisted jobs across workers; no custom realtime
dispatcher lease is required.

Use a transactional outbox only for events whose loss would affect payroll,
accounting, compliance, or another business-critical process. Such events should not
depend on browser SignalR delivery as their source of truth.
