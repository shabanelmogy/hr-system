| D-020 | Currency master ownership | Approved at Phase 00 preflight; rebaseline clarified 2026-09-21 | Accounting owns the company Currency master from the development baseline. `InitialAccounting` owns `acc.Currencies`; HR never owns or persists a writable Currency master and `InitialHr` must not create `hr.Currencies`. HR keeps business/financial facts as CurrencyCode snapshots and validates new or changed codes through the stable Accounting `IAccountingCurrencyCatalog`. No demo-data preservation or Currency cutover migration is required. Former HR `IsDefault`/`ExchangeRateToDefault` semantics are not retained, migrated, or backfilled; Functional Currency is established later through normal `AccountingCompanySettings` setup together with Primary Book, while Accounting owns historical FX. | Finance is the owning bounded context anticipated by the earlier Geography/Countries design; a clean development baseline removes legacy ownership and dual authority instead of preserving transitional demo state | Accounting + HR + Web + Mobile + baseline persistence |
| D-021 | Company accounting settings | Approved at Phase 00 preflight | One company-scoped `AccountingCompanySettings` singleton stores `FunctionalCurrencyId` and `PrimaryBookId` with RowVersion. Currency identity remains in `Currency`; Book remains ledger configuration. Future adjustment books reuse the same company functional currency. | Keeps DEC-008 company policy out of Book identity and avoids deriving accounting policy from HR's former `IsDefault` flag | Accounting setup + persistence |
| D-022 | Typed mapping availability | Approved at Phase 00 preflight | `AccountMapping`/Posting Profiles keep typed source references, but a source-specific mapping type is exposed only when the owning source Contract exists. Slice 1 always supports company-purpose defaults; absent BankAccount/PaymentMethod/Cashbox/ContactGroup/PartyRole masters are not synthesized. | Preserves D-017 without fake masters, dead FKs, or UI options that cannot validate | Link Accounts + integrations + clients |
| D-023 | Slice 1 execution decomposition | Approved 2026-09-22 | Keep `accounting-ledger-setup` as the Slice 1 umbrella for integration/history evidence and final verification; execute future Slice 1 work through child packages `1A Currency`, `1B COA/Hierarchy`, `1C Dimensions`, `1D Books/Journals`, `1E Company Settings`, `1F Exchange Rates`, `1G Link Accounts`, `1H Posting Profiles`, then `1V Integration/Verification`. Each child owns typed transport/API boundaries and an explicit Screen Contract. The current generic `LedgerSetupRecord`/resource renderer is evidence to refactor, not the target architecture. COA Web composition reuses `SplitTreeView` and the Cost Center master/detail interaction pattern without copying HR domain logic. | Keeps the business slice coherent while making implementation/review small, typed and independently verifiable | Plan + API + Web + Mobile + documentation workflow |
| D-024 | Account code proposal baseline | Approved 2026-09-22 | The server proposes a company-wide, non-hierarchical `ACC-####` convenience code using the next reserved numeric suffix. Archived codes remain reserved. The proposal is not a reservation or hierarchy rule: an authorized user may edit it, hierarchy is always determined by `ParentAccountId` + `AccountHierarchyLevelId`, and the database unique key remains authoritative. Concurrent callers may receive the same proposal; one create wins and the loser receives the stable duplicate conflict and requests a fresh proposal. | Makes D-014 executable without encoding hierarchy into account codes or adding a hidden client-side generator/sequence owner | COA Application/API/Web/Mobile/tests |
| D-025 | Accounting mock-data action | Approved 2026-09-23 | Every writable Accounting data-entry journey on Web and Mobile exposes the shared `MyForm`/`AppForm` mock-data action when its required authoritative prerequisites are loaded. The action fills a realistic valid local draft only; it never submits/persists, invents IDs or RowVersion, assigns tenant/company/auth/posting state, or replaces server proposals/lookups. Read-only, report-only, and query-only screens are N/A and expose no fabricated data. Web availability is not gated by `NODE_ENV`; Mobile keeps the central `MockDataPreferencesProvider`. Any later commercial visibility switch is a central platform setting, never a feature-local flag. | Hosted-trial usability while preserving server authority and one cross-platform interaction contract | Accounting forms + Web/Mobile shared forms/tests/docs |
| D-026 | Vertical slice gate | Approved 2026-09-23 | Revalidate and close one feature step end to end in the fixed order `API → Web → Mobile → live API-backed verification → documentation/closure`; the next step cannot start until integrated live verification is `Verified` and documentation/closure is `Closed`. Historical child package IDs (`1A`–`1V`) remain stable; the human execution sequence starts with Step 01 Fiscal Years & Periods, then Step 02 Currency, followed by COA/Hierarchy and the remaining children. | Prevents implementation drift between platforms and makes every handoff reviewable before business scope expands | Plan + API + Web + Mobile + verification evidence |
| D-027 | Screen pattern evidence | Approved 2026-09-23 | Every screen contract must declare its canonical Pattern ID and reviewed reference, platform adaptation, required views, form/detail shape, loading/empty/error/permission states, mock-data decision, and verification evidence. A generic “shared component reused” statement is insufficient. Fiscal Years uses P-001 Server-managed Grid/CRUD; its generated periods are a read-only child preview and P-003 tabs are intentionally not applied. | Makes the agreed UI pattern library executable and prevents each module from inventing an untracked layout | Screen contracts + Web/Mobile guides + tests |
