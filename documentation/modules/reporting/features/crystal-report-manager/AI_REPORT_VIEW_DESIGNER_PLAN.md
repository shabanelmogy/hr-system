# AI Report View Designer Implementation Plan

Status: **Planned**

Scope: Reporting control plane + Crystal report design-time data-source workflow

Initial AI provider: **DeepSeek API**

Runtime policy: **Crystal Runtime remains database-isolated and DataSet-driven**

This document is the implementation plan for adding AI-assisted report data-source
design to the ERP Reporting module. It deliberately separates report **design-time
schema discovery** from report **runtime data access**.

The target workflow is:

```text
Admin prompt
    -> Reporting AI planner
    -> constrained structured report plan
    -> deterministic SQL View generator
    -> application-side validation
    -> bounded preview
    -> administrator approval
    -> publish managed SQL View
    -> extract immutable schema snapshot
    -> register Crystal data-source contract
    -> prepare/edit .rpt in external Crystal Reports Designer

Runtime remains:

Browser / Mobile
    -> Reporting API
    -> entity-specific Reporting data provider
    -> owning module Contracts
    -> authorized projection
    -> explicit-schema DataSet
    -> Crystal Runtime
    -> SetDataSource(DataSet)
    -> PDF
```

The SQL View created by this feature is therefore a **managed design/schema
contract** for Crystal reports. It is not permission to reconnect the Crystal
Runtime to the ERP database and it is not a replacement for the existing
`ICrystalReportDataProvider` runtime boundary.

---

## 1. Goals

The feature must make it practical for an administrator to describe a report in
business language and obtain a safe, reviewable Crystal data-source definition
without turning an LLM into a database administrator.

The completed capability should allow an authorized administrator to:

1. enter a natural-language report requirement;
2. generate a structured report-source plan with DeepSeek;
3. inspect the proposed entities, joins, fields, filters, and calculated concepts;
4. inspect deterministic SQL generated by ERP code;
5. validate the proposal against Reporting rules and SQL Server metadata;
6. preview a bounded sample;
7. explicitly publish a managed View;
8. register the published View and its schema as a Crystal data-source contract;
9. later prepare or refresh a `.rpt` schema for editing in external Crystal
   Reports Designer;
10. create a new immutable source version when requirements change and evaluate
    the impact before publishing it.

This capability must be suitable for a large ERP: deterministic, auditable,
permission-aware, module-aware, versioned, testable, and replaceable at the AI
provider boundary.

## 2. Non-goals and hard boundaries

The following are architectural rules, not MVP shortcuts:

- DeepSeek never receives a database connection string, database credentials, API
  secrets unrelated to its own provider, or unrestricted database metadata.
- DeepSeek never executes SQL and never owns `CREATE VIEW`, `ALTER VIEW`, or any
  database command.
- Raw AI-generated SQL is never the trusted execution contract.
- The AI receives only an allowlisted Schema Catalog and Semantic Catalog prepared
  by the ERP application.
- A browser or mobile client never sends SQL, a connection string, a physical
  database name, tenant ID, company ID, storage path, or Crystal filesystem path.
- Publish is a separate action from Generate. Generation must never automatically
  create or alter a database object.
- Crystal Runtime remains disconnected from ERP SQL and continues to receive
  pushed explicit-schema data from the Reporting API.
- The published View is primarily a design-time/schema contract. Runtime business
  authorization and data truth continue to belong to the owning module and its
  Reporting provider.
- The AI feature lives in the `.NET 10` Reporting module/control plane. Do not add
  DeepSeek, SQL generation, business metadata, or database publishing logic to the
  `.NET Framework 4.8` Crystal Runtime.
- Crystal Reports Designer remains the report-layout editor. This plan does not add
  a browser Crystal designer.
- A published source definition is not silently overwritten. Changes create a new
  version/draft and pass validation and impact analysis before publish.

## 3. Architectural placement

The feature belongs under the Reporting bounded context and should use the normal
module flow:

```text
Controller
    -> ISender
    -> command/query handler
    -> Reporting application ports
    -> Reporting infrastructure adapters
```

Suggested logical feature name:

`AiReportDataSources`

Suggested domain aggregate name:

`ReportDataSourceDefinition`

Suggested immutable revision entity:

`ReportDataSourceVersion`

The exact namespaces should follow the existing Reporting module conventions when
implementation begins. The important boundary is that AI planning, SQL generation,
publication, versioning, and schema registration are Reporting responsibilities;
owning business modules remain the source of business truth.

## 4. Managed source lifecycle

Use an explicit lifecycle. Initial states:

```text
Draft
  -> Planned
  -> Validated
  -> Published
  -> Archived
```

Recommended rules:

- `Draft`: prompt and editable administrator intent exist; no trusted plan yet.
- `Planned`: a normalized AI plan has been accepted structurally but has not passed
  database/application validation.
- `Validated`: deterministic SQL and business/schema rules are valid for the exact
  plan version.
- `Published`: an approved database View and immutable schema snapshot exist and
  are registered for Crystal design use.
- `Archived`: no longer offered for new Crystal source selection; historical
  reports/versions remain auditable.

Do not allow direct transitions from `Draft` or `Planned` to `Published`.

For long-term maintainability, publish immutable `ReportDataSourceVersion` records
instead of replacing the content of a published version. A logical
`ReportDataSourceDefinition` owns the stable key and a pointer to the currently
published version.

## 6. Structured AI planning contract

DeepSeek should return a constrained plan, not executable SQL.

Illustrative shape:

```json
{
  "moduleKey": "reference-data",
  "suggestedKey": "countries",
  "suggestedViewName": "V_Countries",
  "sources": [
    {
      "sourceKey": "countries",
      "alias": "c"
    }
  ],
  "columns": [
    {
      "source": "c",
      "field": "Id",
      "outputName": "Id"
    },
    {
      "source": "c",
      "field": "Code",
      "outputName": "Code"
    },
    {
      "source": "c",
      "field": "NameAr",
      "outputName": "NameAr"
    },
    {
      "source": "c",
      "field": "NameEn",
      "outputName": "NameEn"
    },
    {
      "source": "c",
      "field": "IsActive",
      "outputName": "IsActive"
    }
  ],
  "filters": [
    {
      "source": "c",
      "field": "IsDeleted",
      "operator": "equals",
      "value": false
    }
  ],
  "joins": [],
  "orderHints": [],
  "businessRules": []
}
```

The real DTO should use enums/discriminated contracts rather than free-form
operators. Unknown fields, operators, aliases, source keys, or plan properties must
fail validation.

The LLM may suggest a View name, but the application owns the canonical database
schema and final name. Never concatenate an unvalidated model-provided identifier
into SQL.

## 7. Schema Catalog

The Schema Catalog is the technical allowlist presented to the AI and SQL
generator. It is not an unrestricted reflection of `INFORMATION_SCHEMA`.

Each source entry should describe only fields approved for reporting:

```text
Module: ReferenceData
Source: countries
Physical source: controlled server-side mapping only
Fields:
  Id         uniqueidentifier  required   reportable
  Code       nvarchar(...)     required   reportable
  NameAr     nvarchar(...)     required   reportable
  NameEn     nvarchar(...)     required   reportable
  IsActive   bit               required   reportable
  IsDeleted  bit               internal-filter-only
```

Catalog metadata should be able to express:

- stable logical source key;
- owning module;
- approved physical source mapping known only server-side;
- column name and SQL/application type;
- nullability;
- report visibility (`selectable`, `filter-only`, hidden);
- sensitivity classification;
- allowed joins/relations;
- global / tenant / company scope;
- soft-delete policy;
- maximum expected cardinality or reporting risk hints;
- deprecation state.

The AI sees logical report metadata, not credentials or unrestricted physical
database topology.

## 8. Semantic Catalog

Schema metadata alone cannot encode ERP business meaning. The Semantic Catalog
adds business rules that prevent syntactically valid but materially wrong reports.

Examples:

```text
Concept: Net Sales
Owner: PointOfSale / Accounting integration contract
Rule: exclude draft/cancelled transactions
Rule: returns reduce net amount
Rule: use posted business date
Scope: authenticated tenant + company
```

It should support:

- business concepts and descriptions;
- allowed measures and dimensions;
- approved calculated expressions represented structurally;
- lifecycle exclusions (draft, cancelled, archived, soft-deleted);
- currency/date semantics;
- tenant/company requirements;
- ownership and source-module constraints;
- joins that are meaningful in business terms;
- known ambiguity notes for the AI planner.

The Semantic Catalog should evolve incrementally. The MVP needs enough metadata for
one narrow reference source; complex Accounting/Inventory concepts should be added
only with explicit business ownership.

## 9. Deterministic SQL generation rules

ERP code generates SQL from a validated plan. The generator must not accept raw SQL
fragments from the AI or client.

For a simple plan the output may be:

```sql
CREATE VIEW reporting.V_Countries
AS
SELECT
    c.Id,
    c.Code,
    c.NameAr,
    c.NameEn,
    c.IsActive
FROM ReferenceData.Countries AS c
WHERE c.IsDeleted = 0;
```

The physical schema/table shown above is illustrative; implementation must use the
actual approved server-side catalog mapping.

The generator should initially support only a deliberately small grammar:

- allowlisted source(s);
- explicit column projection;
- approved equality/range/null predicates;
- approved inner/left joins from catalog relations;
- approved deterministic calculated expressions;
- no `SELECT *`;
- no arbitrary functions;
- no query hints;
- no temp tables;
- no dynamic SQL;
- no stored procedure calls;
- no cross-database names;
- no linked servers;
- no system catalog access.

Adding grammar features later must be explicit and tested. Do not create a generic
SQL passthrough merely to support unusual prompts.

## 10. Validation pipeline

Validation occurs after plan normalization and SQL generation and before preview or
publish.

Minimum validation pipeline:

1. **Contract validation** — required plan fields, enum values, identifiers, counts,
   and payload limits.
2. **Catalog validation** — every source, field, relation, filter, and expression is
   allowlisted.
3. **Ownership validation** — joins comply with module ownership and approved
   reporting contracts.
4. **Sensitivity validation** — hidden/restricted columns cannot be projected or
   leaked through expressions.
5. **Scope validation** — tenant/company/global rules are consistent with the
   source contract.
6. **SQL AST/token validation** — generated SQL contains only the grammar emitted
   by the deterministic generator.
7. **Database compile validation** — validate names/types against the target SQL
   Server without publishing the View.
8. **Result schema validation** — output column names are unique, valid, bounded,
   and map to supported Crystal/ADO.NET types.
9. **Complexity validation** — enforce source/join/column ceilings and reject
   obviously unsafe plans. Query-plan/cost thresholds can be hardened in a later
   phase.
10. **Business-rule validation** — required Semantic Catalog rules are represented
    and no forbidden lifecycle/scope omission exists.

At minimum, reject plans or SQL involving:

- `INSERT`, `UPDATE`, `DELETE`, `MERGE`;
- `DROP`, arbitrary `ALTER`, `TRUNCATE`;
- `EXEC` / `EXECUTE`;
- dynamic SQL;
- cross-database or linked-server references;
- system tables/catalogs not explicitly used internally by the validator;
- unapproved tables/views;
- sensitive columns;
- invalid tenant/company semantics;
- invalid module ownership;
- duplicate output columns;
- invalid or collision-prone View names;
- unsupported joins, expressions, or functions.

Never rely on blacklist text matching as the sole validator. The safest design is
to generate SQL only from a typed internal AST/plan whose grammar cannot represent
dangerous statements.

## 11. Preview contract

Preview exists to help the administrator verify meaning before publication.

Rules:

- preview uses the validated structured plan, not arbitrary SQL from the client;
- preview row count is small and server-bounded;
- execution timeout is short and explicit;
- preview result size is bounded by rows and bytes;
- tenant/company rules are applied according to the catalog contract;
- sensitive columns remain unavailable even if requested in the original prompt;
- no mutation or database object creation occurs;
- preview returns column metadata plus sample rows and validation warnings;
- failures use stable application error codes rather than leaking raw provider or
  database exception messages.

For global ReferenceData sources, preview may be global according to the existing
module contract. Tenant/company-owned sources require a deliberate server-derived
scope; the client must not choose tenant/company identifiers.

## 12. Publish contract

`Generate` and `Publish` are intentionally separate operations.

Publishing should require:

- publish permission;
- the latest `RowVersion` for the logical definition;
- a validated immutable source version;
- unchanged Schema/Semantic Catalog versions or an explicit revalidation;
- unchanged generated SQL hash;
- successful final compile/schema validation;
- administrator confirmation.

Publishing through `IReportViewPublisher` should:

1. acquire a logical source-definition lock;
2. reload/revalidate the current version;
3. create or update only the server-owned managed View name;
4. read the resulting database schema;
5. compute and persist SQL/schema hashes;
6. persist the immutable schema snapshot;
7. move the logical published-version pointer atomically where possible;
8. write an audit event;
9. return the published source metadata without returning credentials or an
   unrestricted physical connection contract.

During development, direct `CREATE VIEW` / `ALTER VIEW` from the Reporting
Infrastructure adapter is acceptable for the MVP if it remains behind
`IReportViewPublisher`. Production deployment strategy can later change to a
migration/deployment agent without changing the domain/application contract.

## 13. Crystal data-source registration

After successful View publication, extract the result schema and register a
Crystal design source.

Suggested registration data:

- stable source definition ID/key;
- published source version ID;
- logical source key, for example `reference-data-countries`;
- managed View name, for example `reporting.V_Countries`;
- immutable schema snapshot;
- schema hash;
- supported Crystal field mapping;
- source status;
- owning module;
- published timestamp.

The Crystal-facing schema should be explicit and deterministic: field name, data
type, nullability, ordinal, and any supported length/precision/scale metadata.

Registration does **not** grant Crystal Runtime database access. It gives the
design/preparation workflow a known schema contract that can later be represented
inside a `.rpt`.

## 14. Crystal RPT preparation integration

This is a later phase and should not block the AI/View MVP.

Target flow:

```text
Published managed View
    -> extracted schema snapshot
    -> Crystal source preparation service/tooling
    -> .rpt contains the intended database-field schema
    -> administrator opens .rpt in external Crystal Reports Designer
    -> administrator edits layout/formulas
    -> .rpt is uploaded/imported into normal Crystal Report Manager lifecycle
```

The preparation mechanism may need a controlled design-time connection because SAP
Crystal Designer requires database metadata to establish fields. That design-time
concern must remain separate from production render architecture.

The production runtime contract does not change:

- no ERP DB credentials in Crystal Runtime;
- managed `.rpt` still passes source inspection;
- Reporting still produces the explicit DataSet;
- Crystal Runtime calls `SetDataSource(data)`;
- runtime never trusts the View for authorization or scope.

Before implementing automatic RPT preparation, prove with one real `.rpt` that a
View-derived design schema remains compatible with the pushed DataSet schema used
at runtime.

## 15. Versioning and impact analysis

Once a source is published, edits create a new draft version.

Example:

```text
Countries source
  V1 Published
  V2 Draft -> Planned -> Validated
  impact analysis
  V2 Published
```

Before publishing a schema-changing version, compare the proposed schema to the
currently published snapshot and classify changes:

- additive field;
- removed field;
- renamed field;
- type change;
- nullability change;
- precision/scale/length change;
- semantic/source ownership change.

Breaking changes require impact analysis against Crystal reports registered to the
source.

Example warning:

```text
Breaking change
Source: reference-data-countries
Removed field: NameEn
Affected reports:
  CountriesSummary.rpt
  CountriesDirectory.rpt
```

Do not automatically rewrite Crystal formulas or layouts to repair breaking
changes. The report owner updates the `.rpt` in Crystal Designer and publishes a
new report version through the existing manager workflow.

## 16. Permissions

Use module-local Reporting permissions and align exact naming with existing
`ReportingPermissions` conventions during implementation.

Proposed capabilities:

```text
Reporting:AiDataSources:View
Reporting:AiDataSources:Generate
Reporting:AiDataSources:Validate
Reporting:AiDataSources:Publish
Reporting:AiDataSources:Archive
```

If the project convention favors a different separator/name layout, use that
canonical convention rather than introducing a second permission style.

Suggested behavior:

- View: list/read definitions, versions, validation and schema metadata.
- Generate: create drafts and call the AI planner.
- Validate: run application/database validation and bounded preview.
- Publish: create/change managed View objects and published pointer.
- Archive: retire a logical source from new usage.

All mutations must also respect normal read-only/system-mode restrictions used by
the ERP platform.

## 17. Audit requirements

The feature should be fully explainable after the fact without logging secrets.

Audit at least:

- source definition created;
- prompt submitted/generated;
- AI provider/model identifier;
- normalized plan hash;
- validation requested/result;
- preview requested/result metadata, not full sensitive result rows;
- publish requested/completed/failed;
- SQL hash and schema hash;
- publisher identity;
- archive action;
- version transition;
- impact analysis result for breaking schema changes.

Never log:

- DeepSeek API key;
- DB credentials/connection strings;
- unrestricted database metadata;
- full sensitive preview rows;
- arbitrary raw exception bodies from external AI/database providers.

## 18. Frontend experience

Add a `Data Sources` section/tab to Reporting/Crystal administration after the API
foundation is stable.

Suggested workflow:

```text
Data Sources
  -> Create with AI
  -> Prompt
  -> Generate Plan
  -> Review Sources / Fields / Business Rules
  -> Review Generated SQL
  -> Validate
  -> Preview Sample
  -> Publish
  -> View Schema / Versions / Impact
```

The frontend sends business intent and stable IDs only. It does not construct or
edit executable SQL in a free-form editor for the MVP.

Recommended UI states:

- draft;
- generating;
- AI provider unavailable;
- plan invalid;
- validation failed;
- validated;
- preview loading/success/failure;
- publish confirmation;
- stale `409` with reload/discard-stale behavior;
- published;
- breaking-change warning;
- archived.

SQL preview is read-only. If manual SQL editing becomes a future requirement, it
must be designed as a separate trusted expert workflow with its own parser,
validation, permissions, and audit policy; it must not be smuggled into this MVP.

## 20. Configuration — development first

Initial DeepSeek configuration should live in the Reporting Infrastructure host
configuration and be bound to validated options.

Conceptual settings:

```text
Reporting:Ai:Provider = DeepSeek
Reporting:Ai:DeepSeek:BaseUrl
Reporting:Ai:DeepSeek:ApiKey
Reporting:Ai:DeepSeek:Model
Reporting:Ai:TimeoutSeconds
Reporting:Ai:MaxPromptCharacters

```

The API key must come from a development secret/environment/user-secret mechanism,
not from a browser and not from the database definition model. Production secret
hardening is intentionally deferred until deployment work, consistent with the
current development stage.

## 21. Testing strategy

Testing should be layered so AI availability is never required for ordinary domain
and SQL-generation tests.

### Domain tests

- lifecycle transitions;
- immutable published versions;
- version numbering;
- publish/archive rules;
- source-key and View-name invariants;
- stale `RowVersion` behavior;
- schema-change classification.

### Application tests

- permission enforcement;
- planner input contains only approved catalog metadata;
- malformed AI plans rejected;
- unsupported source/column/join/operator rejected;
- Generate does not Publish;
- validation required before Publish;
- catalog drift forces revalidation;
- publisher called only for exact validated version;
- stable error mapping for AI/database failures.

### SQL generator tests

- deterministic SQL for the same normalized plan;
- explicit projection, never `SELECT *`;
- identifier quoting/canonicalization;
- allowed filters/joins;
- forbidden constructs cannot be represented;
- no raw AI/client SQL fragment enters generated output;
- hash stability.

### Infrastructure tests

- DeepSeek response parsing and bounded body handling;
- timeout/cancellation;
- malformed JSON/provider failure mapping;
- SQL compile validation;
- preview row/byte/time limits;
- managed View publication;
- schema extraction types/nullability/ordinal;
- transactional/locking semantics where supported.

### Integration tests

- create -> generate -> validate -> preview -> publish;
- publish conflict returns `409` and no partial state;
- database object and persisted published version agree;
- schema snapshot/hash agree with published View;
- tenant/company rules where applicable;
- audit events;
- report-source registration.

### Frontend tests

- permissions;
- loading/error/empty states;
- exact request DTOs;
- generated plan rendering;
- read-only SQL preview;
- validation warnings;
- bounded preview UX;
- publish confirmation;
- `409` reload/discard-stale flow;
- version/impact display.

### Crystal acceptance test

Before declaring the complete feature production-ready, use a genuine `.rpt` to
prove:

1. the published View supplies the intended design-time fields;
2. Crystal Designer sees those fields;
3. the report is saved with the required managed `Language` parameter and current
   source-policy requirements;
4. the same report can be uploaded/imported into Report Manager;
5. runtime rendering succeeds with an explicit DataSet and no ERP DB connection in
   Crystal Runtime.

No existing test currently proves this real-RPT loop; it remains an acceptance
gate, not something to assume from unit tests.

## 22. Phased implementation

### Phase 0 — Contract and decisions

### Objective

Freeze the feature vocabulary and non-negotiable boundaries before code is added.

### Work

- choose final aggregate/feature naming;
- define lifecycle states and versioning model;
- define stable source-key and managed View naming rules;
- define the first MVP business source (`Countries` is recommended);
- define initial structured plan DTO and supported grammar;
- define what Schema Catalog metadata is visible to the AI;
- define the minimum Semantic Catalog fields;
- define permission names using existing Reporting conventions;
- define Preview and Publish separation;
- record that Crystal Runtime remains DB-isolated/DataSet-driven;
- decide development SQL publication strategy behind `IReportViewPublisher`.

### Entry criteria

- current Crystal Report Manager architecture remains green;
- user-approved direction to use DeepSeek is recorded;
- one MVP source can be identified without cross-module ambiguity.

### Exit criteria

- contracts are written and reviewed;
- no unresolved question changes the trust boundary;
- MVP scope is one simple source with explicit fields and no arbitrary SQL.

### Deliverable

An implementation-ready contract/spec update and DTO sketches.

### Phase 1 — Foundation: domain, persistence, CQRS, permissions

### Objective

Create the managed source-definition lifecycle without AI or database publishing.

### Work

- add `ReportDataSourceDefinition` aggregate;
- add immutable `ReportDataSourceVersion` model;
- add status/lifecycle invariants;
- add EF configuration/migration;
- add commands/queries and validators;
- add coarse permissions;
- add `RowVersion` concurrency where writes require it;
- add repository/application ports as needed;
- add audit hooks/events;
- expose basic list/detail/create/archive API;
- add domain/application tests.

### Entry criteria

- Phase 0 contract is frozen.

### Exit criteria

- a draft definition can be created/read/versioned/archived;
- published content cannot be overwritten in place;
- permission and concurrency tests pass;
- no AI/database-specific dependency leaks into Domain.

### Deliverable

Stable managed-data-source lifecycle ready for planning.

### Phase 2 — Schema Catalog and Semantic Catalog

### Objective

Build the only metadata surface the AI and SQL generator are allowed to consume.

### Work

- implement `IReportSchemaCatalog`;
- model approved sources, fields, types, relations, sensitivity and scope;
- add one canonical `Countries` catalog entry;
- implement initial `IReportSemanticCatalog`;
- describe Countries lifecycle/reporting semantics;
- add source/module ownership validation;
- add catalog version/hash so an AI plan can be tied to exact metadata;
- ensure physical names stay server-side where possible;
- test that hidden/unapproved fields never appear in the AI planning context.

### Entry criteria

- Phase 1 lifecycle exists;
- ownership of the MVP source is known.

### Exit criteria

- the system can produce a bounded versioned catalog snapshot for the MVP source;
- only approved report metadata is exposed;
- sensitivity/scope/ownership information is machine-validatable;

## 23. Concrete MVP walkthrough — Countries

This is the reference scenario for the first implementation.

### Administrator prompt

```text
Create a data source for a Countries Crystal report.
I need country code, Arabic name, English name and active status.
Do not include deleted countries.
```

### AI receives

Only the approved ReferenceData Countries Schema/Semantic Catalog entry. It does
not receive a DB connection string and cannot inspect unrelated tables.

### DeepSeek returns a structured proposal

```json
{
  "moduleKey": "reference-data",
  "suggestedKey": "countries",
  "suggestedViewName": "V_Countries",
  "sources": [
    { "sourceKey": "countries", "alias": "c" }
  ],
  "columns": [
    { "source": "c", "field": "Id", "outputName": "Id" },
    { "source": "c", "field": "Code", "outputName": "Code" },
    { "source": "c", "field": "NameAr", "outputName": "NameAr" },
    { "source": "c", "field": "NameEn", "outputName": "NameEn" },
    { "source": "c", "field": "IsActive", "outputName": "IsActive" }
  ],
  "filters": [
    { "source": "c", "field": "IsDeleted", "operator": "equals", "value": false }
  ],
  "joins": []
}
```

### ERP application generates SQL

Illustrative output:

```sql
CREATE VIEW reporting.V_Countries
AS
SELECT
    c.Id,
    c.Code,
    c.NameAr,
    c.NameEn,
    c.IsActive
FROM ReferenceData.Countries AS c
WHERE c.IsDeleted = 0;
```

### ERP validates

- source is allowlisted;
- fields are allowlisted;
- `IsDeleted` is valid as a required internal filter;
- no sensitive field is exposed;
- no invalid cross-module join exists;
- SQL grammar is generated, not model-supplied;
- SQL compiles;
- result schema is Crystal-compatible.

### Administrator previews

The application executes a bounded non-publishing preview and returns a few rows
plus column metadata.

### Administrator publishes

The application revalidates, calls `IReportViewPublisher`, creates the managed
View, extracts the exact schema, records audit/hashes, and marks the immutable
version Published.

### Crystal source registration

Logical source:

```text
reference-data-countries
```

Design View:

```text
reporting.V_Countries
```

Registered fields include `Id`, `Code`, `NameAr`, `NameEn`, and `IsActive`.

### Later RPT preparation

A Countries `.rpt` is prepared using that schema, opened in Crystal Reports
Designer, and edited normally.

### Production render remains unchanged

```text
Countries Reporting provider
    -> IReferenceDataReportingSource
    -> authorized rows
    -> explicit ReportData DataSet
    -> Crystal Runtime
    -> Countries.rpt
    -> SetDataSource(DataSet)
    -> PDF
```

The Crystal worker does **not** execute `SELECT * FROM reporting.V_Countries`.

## 24. Rollout order

Implement in this order:

```text
0. Freeze contracts
1. Domain/persistence/CQRS/permissions
2. Safe Schema + Semantic Catalog
3. DeepSeek structured planner
4. Deterministic SQL generator + validator
5. Preview + explicit publish
6. Schema extraction + Crystal source registry
7. One real RPT preparation/render proof
8. Versioning/impact/frontend/hardening
```

Do not start with frontend polish or automatic RPT manipulation. The first proof
should establish the trust boundary and data-source lifecycle end to end.

## 25. MVP completion gate

The first MVP is complete when all of the following are true:

- [ ] Countries is represented in the approved Schema Catalog.
- [ ] Minimum Countries business semantics are represented in the Semantic Catalog.
- [ ] DeepSeek receives only bounded allowlisted metadata.
- [ ] DeepSeek returns a strict structured plan, not trusted SQL.
- [ ] ERP code deterministically generates the View SQL.
- [ ] Forbidden SQL cannot enter the generator contract.
- [ ] Validation succeeds before Preview/Publish.
- [ ] Preview is bounded and performs no database mutation.
- [ ] Publish requires explicit permission, confirmation, and concurrency token.
- [ ] A managed Countries View is published through `IReportViewPublisher`.
- [ ] SQL hash and schema hash are persisted.
- [ ] Published schema is extracted and registered as a Crystal design source.
- [ ] AI and client never receive DB credentials.
- [ ] Crystal Runtime remains disconnected from ERP SQL.
- [ ] Existing DataSet-based runtime path is unchanged.
- [ ] Focused domain/application/infrastructure tests pass.

Phase 7 adds the decisive acceptance gate: a real `.rpt` must prove that the
View-derived design schema and the pushed runtime DataSet remain compatible.

## 26. Final architectural rule

The feature may use AI to understand **intent**, but authority remains in ERP code:

```text
AI proposes.
ERP validates.
ERP generates SQL.
Administrator approves.
ERP publishes.
Owning modules provide runtime business data.
Crystal Runtime only renders pushed data.
```

That separation is the foundation that allows DeepSeek to add useful automation
without turning report generation into an unrestricted SQL or database-access
surface.
