# Legacy analysis

## Purpose

Understand what the existing system really does — screens, workflows, data, authorization,
integrations — and what it does wrong, with evidence from the code. The legacy system is
**business evidence**, not the blueprint for the new architecture.

## Inputs

- Source path (read-only), and how to run it if possible.
- `planning/legacy/inventory.md` (generated by `New-PlanningWorkspace.ps1 -Mode Migrate`, or run
  `templates/conversion/Analyze-NextProject.ps1 -Source <path> -Output planning/legacy/inventory.md`).
- Database schema or ORM models; environment variable names (never values).

## Procedure

### A1 — Complete the inventory

The analyzer covers Next.js App Router pages, route handlers, `"use server"` files, Prisma model
names, and common auth/data packages. Extend the inventory by hand for everything else:

| Look for | Where |
| --- | --- |
| Pages Router screens and API routes | `pages/**`, `pages/api/**` |
| Separate Node backend | Express/Fastify/Nest routers, controllers, middleware, guards (`app.get(`, `router.post(`, `@Controller`) |
| Server Actions by function | exported functions inside `"use server"` files |
| Data model detail | Prisma fields, relations, `@unique`, `@default`, enums; Mongoose/Sequelize/TypeORM models; raw SQL |
| Authorization | middleware, `auth()`/`currentUser()`/session role checks, route guards, hidden-but-reachable UI |
| Background work | cron, queues, webhooks, scheduled functions |
| Integrations | payment, email/SMS, storage (Cloudinary/S3), external APIs |
| Configuration | `.env.example`, config files (names and purpose only) |
| Tests | what is tested at all |

Every inventory item gets a stable reference (`SCR-01`, `API-07`, `ACT-12`, `MDL-03`, `JOB-02`).

### A2 — Behavior catalog

For each screen, endpoint, and action write an entry in `legacy/behavior-catalog.md`:

- actor(s) and how they reach it
- inputs and validations (client and server — note when they differ)
- data read and written (models/fields)
- side effects (emails, uploads, external calls)
- authorization **actually enforced** on the server, not what the UI hides
- observed rules → add to `06-business-rules.md` as `Draft`, evidence `[legacy:path#Lnn]`
- relationships → note for `05-domain-model.md`

Cite evidence as `[legacy:src/app/actions.ts#L42]`. If behavior is unclear from code, write it
as a question, not a guess.

### A3 — Defects and dispositions

Record in `legacy/defects.md` with severity and evidence. Typical categories:

- mutations without server-side authorization; detail pages readable by ID (IDOR)
- placeholder or mis-wired actions (e.g. several deletes mapped to one function)
- invariants the database does not enforce (both/neither foreign keys, duplicates)
- race conditions (count-then-insert capacity checks)
- cross-system writes without compensation (auth provider + database)
- hardcoded/demo data presented as real
- unbounded queries, missing pagination, zero-division
- secrets in code, missing validation, missing tests

For each defect ask the owner for a disposition and record it as a decision:
**fix in target**, **preserve deliberately**, or **drop feature**.

### Close the track

1. Ask the UI policy question: preserve the UI exactly, preserve flows but allow visual changes,
   or redesign? Record `D-###`.
2. Ask whether production data must be migrated. If yes, start `data-migration-planning` in
   parallel after C1.
3. Run gate GA (`checklists/gates.md`).

## Outputs

`legacy/inventory.md`, `legacy/behavior-catalog.md`, `legacy/defects.md`, draft rules, relationship
notes, risks (`10-risks.md`), questions, decisions, and `status.md`.

## Quality bar

- Every inventory item is either in the behavior catalog or explicitly out of scope.
- Every rule taken from code has a file-and-line citation.
- Every defect has a disposition decision.

## Anti-patterns

- Translating page → controller or ORM model → entity one-to-one.
- Treating UI visibility as authorization.
- Reproducing broken behavior because "the old system did it" without a decision.
- Copying secrets or real personal data into planning files.
